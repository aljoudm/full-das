# Assumptions of the event model (all in `config/parameters_reviewed.tsv`, column value_type)
* Wadis come from the DEM (cell lower than its 300 m Gaussian mean by `wadi_depth_m` with a gentle floor): a PROXY, the 30 m DSM includes buildings and no wadi map exists.
* Dirt roads = OSM `highway=track|unclassified` (surface is not tagged, so this is a proxy); built-up = distance to the centre of an OSM urban area or place (centre points only, so the 1 km radius is coarse).
* Entry weights (x3 wadi, x2 track, x2 urban), type proportions per terrain class, speeds, durations, heading random walk and the non-intrusion rates are ASSUMED / PLACEHOLDER; none has a source.
* Intrusion arrival is uniform over the 24 h of a day (no night preference modelled).
* A trajectory ends 600 m inside (measured on the local normal) or after 1800 s; about 7 % of the walks leave the boundary polygon at concave bends.

# Assumptions of the DAS stage
* The window length, duration and sampling are PLACEHOLDERS until the AI input is fixed (Yomna). The library is rebuilt by `build_das_library(P, 'Force', true)`.
* Event waveforms: walking, digging and vehicle are those of DAS-Simulation `define_events.m`; running, climbing, animal and the background-noise event are ASSUMED (no source).
* Ground coupling (burial, soil, intruder-to-cable distance) is a log-normal factor with sigma 0.4 and mean 1 (ASSUMED). Detection is therefore dominated by this assumption at long range: the 0.977 is a property of the model, not a measured Pd.
* The detection statistic is the band-limited (8 to 200 Hz) energy of the recovered elongation, peak over channels / median; a plain activity statistic (std of dL) detects far less at long range (S of walking at 18 km about 3, same as noise). Intrinsic false alarms use a normal-tail extrapolation.
* The engine does not model laser phase noise, polarisation fading, splices, real cable coupling or the interrogator's own processing (see DAS-Simulation README); no real FEBUS recording has been compared.

# Assumptions and limits of the classifier (Brno dataset)
* **The labelled Brno data are not enough to estimate the true accuracy of an event classifier.** Each class has between 1 and 4 recordings of 20 to 70 seconds from ONE site, ONE interrogator (Optasense ODH-F), one buried cable and a few people / vehicles. Windows cut from one recording are strongly correlated, so every accuracy we compute has wide confidence limits (bootstrap over recordings) and must always be quoted with them and with the number of recordings. A single accuracy figure without limits and recording counts is not reported anywhere in this repository.
* The published 93.5 % (random windows) is not comparable with our grouped number: random windows put neighbouring windows of the same recording in train and test.
* Classes with ONE recording (running, construction, regular and possibly others) are evaluated with a temporal split of the same recording (first 60 % train, 10 % gap dropped, last 30 % test). Their results are labelled **"same recording, temporal split"** and are optimistic (same person, same place).
* The class `animal` has no data in any public set: its accuracy is a PLACEHOLDER (`Pc_animal_placeholder`).
* The classifier is trained on a different device and site than FEBUS: its accuracy on FEBUS is unknown until real FEBUS recordings exist (Phase 0).
* **Use in the simulation**: the optimization keeps Pc_DAS from the literature (0.983 to 0.993, wang2024). The Brno confusion matrix is used in the unified simulation only for the SHAPE of the errors (what is confused with what). If its accuracy is lower than the literature, both cases are shown as a sensitivity. The simulated-window check (classifier applied to our simulated windows) is a separate "sim-domain check" table and is never mixed with the Brno table.

# Classifier evaluation: deviations from docs/Classifier_Evaluation_Protocol.pdf (23 Nov 2026)
The protocol is applied as far as the Brno data allow. Every deviation and its reason:
1. **Group unit = recording file.** The location along the cable is not given and 12 of 16 recordings are from 2023-04-17, so cable zone x day and day grouping are impossible (`docs/brno_metadata.md`).
2. **Locked test = 4 of 16 recordings (25 %)**, above the 15-20 % target: every evaluable class (>= 2 recordings: walking, vehicle, climbing, other) needs one test recording. Chosen once with seed 20261122 and written to `config/splits.json` before any training; never regenerated.
3. **Evaluable classes: walking (2 recordings), vehicle (4), climbing (3), other (3).** Running, digging (construction), background (regular) and tampering (manipulation) have ONE recording: they stay in training but are out of the headline balanced accuracy and macro F1, which are computed over the evaluable classes only (their number and names are printed next to the number). An event of an evaluable class predicted as one of them counts as an error of its true class.
4. **Running is an ALARM class that is not evaluated on Brno** (1 recording). It has priority when FEBUS data are collected (protocol section 6). The same holds for digging, tampering and the background class.
5. **Single-recording diagnostic (23 Nov rule, replaces 60/10/30):** contiguous blocks, the first 80 % of the recording rows for training, the last 20 % for testing, with a gap of two windows (one window and its overlap) between them. Labelled `[DIAGNOSTIC - SAME RECORDING]`, "same recording, optimistic", never in the headline. See `config/splits_addendum.json`.
6. **Walking has 2 recordings:** one in the locked test, one in development; in the development fold that validates it there is no walking training data. Development folds are descriptive only; no hyper-parameter is tuned (fixed architecture and epochs).
7. **Events** = annotated curves of the json; an event has windows only if the bitmap marks it for at least half a window (1 s: 9 of 14 fence events, 2 s: 3 of 14). Windows of one event overlap and are not independent: evaluation is at event level (mean probability over the windows of an event); window accuracy is shown only as a diagnostic.
8. **Test recordings are fewer than 10**, so the cluster bootstrap interval is too narrow and Clopper-Pearson intervals on events are reported next to it. With a few events per class, no claim of AC0 = 98 % (149 error-free independent events per class) is possible on Brno.
9. **The protocol's class list has fibre tampering as its own class; decision 10 (22 Nov) had merged manipulation with climbing.** `config/class_map.yaml` follows the protocol: tampering is separate (1 recording, not evaluable).
10. **Brno is stored as RAW int16 (20 kHz, 1.02 m channels), not PSD**, contrary to the team report; the gauge length and units are not in the files.

# Decision D3 and the drone camera (23 Nov 2026)
* **D3 is decided: the cable is BURIED** (not fence-mounted). The table row `D3_installation` records it. It changes what FEBUS data are needed (buried cable: ground coupling, depth, soil) and supports the log-normal ground-coupling assumption of the DAS window library (sigma 0.4, ASSUMED); it removes the fence-mounted case of the classifier protocol (section 5 and 8, item 5).
* **Re-identification camera sources:** (a) fixed cameras (1 m position error along the fence, ASSUMED; they cover only 1.9 % of the boundary) and (b) the drone camera, the main source. Drone position error along the fence, one sigma per axis: optimistic 1.5 m and base 2.5 m (PROXY from Nalamothu et al. 2024, arXiv 2410.12556: mean horizontal error 1.3 / 2.5 / 2.9 m at 10 / 20 / 30 m altitude and 3.6 m at 45 degrees, divided by 1.25 for a Rayleigh distribution; the target is static and the GPS type is not stated, so the figures are optimistic), pessimistic 5 m (ASSUMED, source pending).

# Classifier run log (honesty about re-runs)
* The 1 s protocol run was executed TWICE with the same seeds and the same split file: the first run missed the background diagnostic because `splits.json` names the class `background` and the code `no_event` (fixed). **The locked-test numbers are identical in both runs** (balanced accuracy 0.750, recall per class, per-recording results, precision, ECE, model checksum 7bae961b...), so the locked test was not "tuned": only the diagnostics changed (tampering diagnostic recall 0.67 -> 0.33, because the diagnostic model now also holds out the end of the background recording).
* Background diagnostic ([DIAGNOSTIC - SAME RECORDING], same recording, optimistic): 0 alarm-class events among 1 background event with a 1 s window in the last 20 % (16.9 s over 0.075 km = 1.5e-5 km-days): the rule-of-three upper bound is about 205,000 alarms per km per day. It proves nothing; 30 km-days of clean FEBUS background are needed to show an upper bound of 0.1.
